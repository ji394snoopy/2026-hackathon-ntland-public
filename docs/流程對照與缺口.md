# 表單產製流程：步驟對照、Stack / Lambda 來源、缺口盤點

> 單一事實來源，對齊「表一勘查 → 表二評分 → 表三比較 → 結果報告」這條使用者流程，
> 逐步標出對應的 CDK stack、Lambda 來源檔與目前狀態。
>
> 參考文件：
> - [`API_INTEGRATION.md`](../API_INTEGRATION.md) — 對外三階段表單 API 契約
> - [`infra/docs/bedrock-stack-plan.md`](../infra/docs/bedrock-stack-plan.md) — Bedrock/PDF 雛型計畫
> - [`infra/README.md`](../infra/README.md) — infra stack 總覽
>
> 最後更新：2026-09-10（部署基準更新）

> **🔵 部署基準（使用者確認）**：`NtlandAssetStack` / `NtlandDatabaseStack` / `NtlandLambdaStack` /
> `NtlandBedrockStack` **四個 stack 已全部 `cdk deploy`**，DB 初始化也已跑（PostGIS extension +
> 灌 opendata + 建 factor_standard / 案件四表）。因此下方原「🟡 程式碼就位」的 lambda 已升為
> **🔵 已部署**。⚠️ **但「🟢 已驗證」需實際逐一打過 Function URL 端到端確認**——目前尚未逐項實測，
> 故一律停在 🔵、不標 🟢。有斷點（如 graded→前端 mapper 未接線）的另在下方註明。

使用者要對一塊地做地價查估，從頭到尾會這樣操作：

1. **標記地點** — 在地圖上標出比準地（和比較標的）座標，按「開始查詢」。
2. **看表一（勘查表）** — 系統自動查周邊設施、AI 幫忙填好草稿；使用者確認/修改後按「確認」。
3. **看表二（評分）** — 系統依主辦的紙本基準表 + 表一結果，自動評出各因素等級與修正率；使用者確認/修改後按「確認」。
4. **看表三（比較表）** — 系統把表二結果換算成比較法估價表、算出試算價格；使用者確認/修改後按「確認」。
5. **補充圖片** — 使用者上傳其他想放進報告的圖片檔。
6. **產出報告** — 按「下載」，系統產生 PDF 並下載。

> 每一階段都是「**系統先產草稿 → 使用者在畫面上編輯 → 按確認往下一步**」，不是一鍵全自動。

## 1. 核心設計原則

每個階段都遵循「**後端產/查資料（GET）→ 前端顯示並讓使用者編輯 → 使用者定稿回傳（POST）**」。
「產資料」與「用定稿資料產出」是兩支解耦端點，中間隔著人工編輯，後端不一條龍跑完。

## 2. 流程步驟 ↔ Stack / Lambda 對照

### 「完成」定義（全文件通用，先讀）

**未部署 = 未完成。** 程式碼寫完、tsc/build/synth 過，只是「就位」，還沒真正能用。三段式：

| 圖例 | 意義 | 判準 |
|---|---|---|
| 🟡 **程式碼就位** | 寫完、`tsc --noEmit` / `build:lambdas` / `cdk synth` 過 | 尚未 `cdk deploy`、沒有可用 Function URL、（DB 相關）沒建表 |
| 🔵 **已部署** | `cdk deploy` 成功、Function URL 存在、（DB 相關）建表/灌資料跑過 | 還沒實際打過端點驗證回應 |
| 🟢 **已驗證完成** | 實際打過端點、回應正確、端到端串得起來 | 真正「完成」 |
| 🔲 **未實作** | 沒有對應 code | — |

> 目前**整條線沒有任何一項達到 🟢**；絕大多數是 🟡（程式碼就位、待部署）。部署 + 端到端驗證
> 本身是一個獨立、尚未完成的工作項（見 §4「部署與驗證」）。

### 6.2 缺口 ①：基準表數位化結果的儲存與重用（決策 1 + 2 + 3）

**問題**：C-1 目前無狀態，每次都要重傳 PDF、重打 Bedrock。基準表不常變，應存起來重用。

**決策**
- 儲存層：**S3 + 同一個 `NtlandDatabaseStack` 的 Postgres（走 RDS Data API）**，不另開 DB。
- 版本：**依「檔案名稱」累加版本**（同檔名重抽 → version +1），另加一個**標籤欄位**辨識（例如年度/主辦/用途）。
- 存取端點：**獨立的 CRUD Lambda**；`factor-standard-extract` **維持純抽取**，不併入快取邏輯。

**建議 schema（提案，待你定案）** — 掛在既有 `gis` DB：

```sql
CREATE TABLE IF NOT EXISTS factor_standard (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  file_name     text        NOT NULL,           -- 原始檔名（版本以此為累加鍵）
  s3_key        text        NOT NULL,           -- 原始 PDF 在 S3 的路徑
  extracted     jsonb       NOT NULL,           -- 數位化結果（factor-standard-extract 的輸出 JSON）
  version       int         NOT NULL,           -- 同 file_name 內累加：1,2,3...
  label         text,                           -- 標籤：辨識年度/主辦/用途
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (file_name, version)
);
CREATE INDEX IF NOT EXISTS factor_standard_file_name_idx ON factor_standard (file_name);
CREATE INDEX IF NOT EXISTS factor_standard_label_idx     ON factor_standard (label);
```

> S3：可借 `NtlandAssetStack` 或 `NtlandDatabaseStack` 的既有 bucket，或新開一個 `factor-standard/` 前綴的 bucket（待定）。

**新增端點（獨立 CRUD Lambda，建議放 `NtlandBedrockStack` 或新 stack）**
- `POST` 存一筆：收 `{ fileName, s3Key(或直接收 PDF 由此支上傳 S3), extracted, label? }` →
  查該 fileName 目前最大 version、+1 寫入 → 回新版本 metadata。
- `GET` 列表：`?fileName=` / `?label=` 篩選，回版本清單（不含 extracted 大 payload 或可選）。
- `GET` 取單筆：`?id=` 或 `?fileName=&version=`（省略 version 取最新）→ 回 `extracted`。

**與 C-1 的關係（接線，不改 C-1 本身）**
> 前端/orchestrator 流程改成：先呼叫「列表」看有沒有可重用的數位化結果 → 有就直接取回，
> 沒有才呼叫 `factor-standard-extract` 抽 → 抽完呼叫「存」寫回 DB。C-1 lambda 保持純抽取。

狀態：🟡 程式碼就位（`factor-standard-store` CRUD lambda + `factor_standard` 表 + 選項 A wiring 都已寫、synth 過）；
待建表 + deploy + 端到端驗證才算完成。定案：S3 用 `NtlandAssetStack` 的 `dataBucket`、lambda 放 `NtlandBedrockStack`。
計畫見 [`infra/docs/factor-standard-store-plan.md`](./factor-standard-store-plan.md)。
