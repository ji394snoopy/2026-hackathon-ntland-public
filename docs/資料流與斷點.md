## 0. 先把幾個名詞講清楚（讀後面都會用到）

| 名詞 | 白話解釋 |
|---|---|
| **lambda** | 一支跑在 AWS 雲端的後端小程式。前端用一個網址（Function URL）呼叫它，丟資料進去、拿結果回來。這個系統的每個功能（查設施、產表、存檔、產 PDF）各是一支 lambda。 |
| **API / 端點** | 前端呼叫後端的「一個網址 + 一個用途」。例如「產表1（勘查表）」是一個 API，網址是 `POST /api/produce/survey`。 |
| **request（傳入）** | 前端呼叫時**送給**後端的資料。 |
| **response（傳回）** | 後端算完**回給**前端的資料。 |
| **契約** | 「這支 API 該收什麼、該回什麼」的白紙黑字約定。定義在 `API_INTEGRATION.md`。前後端各自照契約做，就能兜起來。 |
| **表1 / 表2 / 表3** | 三張官方估價表單，**照使用者填寫順序命名**：**表1**＝勘查表（記錄這塊地周邊有什麼）；**表2**＝區域因素評分（幫這塊地的區域條件評優劣等級）；**表3**＝比較法估價表（拿幾筆成交案例比一比，算出試算價格）。 |
| **比準地** | 要估價的那塊主角地。 |
| **比較標的** | 拿來跟比準地比較的其他成交案例地（最多 3 筆）。 |
| **草稿 → 編輯 → 確認** | 每張表都是「後端先產一份草稿 → 使用者在畫面上改 → 按確認才進下一張表」，不是一鍵全自動。 |

## 1. 一句話看懂整個系統在做什麼

使用者要幫一塊地估價。系統帶他走三張表單：**先記錄地周邊有什麼（表1 勘查表）→ 幫區域條件評等級（表2 區域因素評分）→ 比一比算出價格（表3 比較法估價表）→ 最後匯出成 PDF 報告**。因為要比價，**比準地和每筆比較標的都要各走一次表1**（累積 1+N 份），這 N+1 份一起送進表2、表3 做比較。每張表都是後端先產草稿、使用者修改確認後再往下。

## 2. 使用者流程（以「畫面 + 動作」為主體）

每個畫面三列：**使用者**做什麼、**觸發 API** 打哪支後端拿什麼資料、**備註**。
每支 API 的詳細輸入/輸出見 §3。

> **關鍵前提（重要）**：這個流程要比價，需要**比準地 + 1～3 筆比較標的**。**每一筆地（含比準地與每個比較標的）都各自走一次「標座標 → 產表1 → 編輯確認」**，累積成 **1+N 份表1 定稿**（最多 1+3 = 4 份）。這 N+1 份**一起**送進表2、表3 做比較評分。所以畫面 1、2 是**對每筆地重複**的。

| 畫面 1｜地圖標記頁（逐筆：比準地，然後每個比較標的） | |
|---|---|
| 使用者 | 在地圖點出「這一筆地」的位置（第一次是比準地，之後是各比較標的），按「開始查詢」 |
| 觸發 API | 按「開始查詢」→ 打 **產表1**（`produce-survey`），送出這筆地的座標，拿回它的表1 勘查表草稿。內部會再打 **查周邊設施**（`ntpc-facilities`）。 |
| 備註 | 整條流程起點。**每一筆地都會走這一步**（比準地 + 各比較標的各一次）。 |

| 畫面 2｜表1 勘查表（可編輯，逐筆） | |
|---|---|
| 使用者 | 看系統填好的周邊設施，逐欄檢查、補上查不到的欄位，按「確認」；然後回畫面 1 標下一筆地，直到比準地 + 所有比較標的都做完 |
| 觸發 API | 按「確認」→ 打 **存檔**（`case-store` `?form=survey`）存這筆地的表1 定稿。全部地做完後，累積成 **1+N 份表1 定稿**。 |
| 備註 | 這 N+1 份表1 是後面表2/表3 比較評分的輸入。 |

| 畫面 3｜表2 區域因素評分（可編輯） | |
|---|---|
| 使用者 | 看系統評出的比準地 vs 各比較標的逐項「優／普通／劣」等級，修改需人工判斷的項目，按「確認」 |
| 觸發 API | 進畫面時 → 打 **產表2**（`regional-factor-grading` 為核心的合併），**一次送 N+1 份表1 定稿**（比準地 + 各比較標的），拿回含比較欄的表2 評分草稿。按「確認」→ 打 **存檔**（`case-store` `?form=regional-factors`）。 |
| 備註 | ⚠️ 「N+1 份表1 → 各自評分 → 合成含比較欄的表2 → 畫面格式」這條串接目前還沒接（斷點 1，見 §4.1）。 |

| 畫面 4｜表3 比較法估價表（可編輯） | |
|---|---|
| 使用者 | 看比準地 vs 各比較標的的逐項差異與試算價格，檢查修改，按「確認」 |
| 觸發 API | 進畫面時 → 打 **產表3**（`POST /api/produce/comparison`），送出「已確認的表2 + **同一批 N+1 份表1／比較標的資料**」，拿回表3 比較法估價表草稿（含試算價）。按「確認」→ 打 **存檔**（`case-store` `?form=comparison`）。 |
| 備註 | ⚠️ 產表3 背後將改為 cli 合併鏈（`delta`=修正率% + `land-transaction` 正常單價 + 試算價），佔位版退役（斷點 2，見 §4.2）。 |

| 畫面 5｜補充圖片頁 | |
|---|---|
| 使用者 | 上傳想放進報告的其他照片 |
| 觸發 API | 每上傳一張 → 打 **上傳圖片**（`image-upload`）存到該案件；進畫面可打它 `GET ?caseId=` 列出已上傳的圖。 |
| 備註 | 契約文件尚未定義這步；⚠️ 匯出時「把圖併進 PDF」還沒接（斷點 3）。 |

| 畫面 6｜輸出頁 | |
|---|---|
| 使用者 | 按「下載」 |
| 觸發 API | 按「下載」→ 打 **匯出**（`fill-report` 合併器），把表1/表2/表3 的 PDF + 三張地圖合併成一份 PDF 下載。 |
| 備註 | ⚠️ 表2/表3 的 PDF 目前沒有雲端來源，合併器會沒東西可合（斷點 3，見 §4.3）。 |

> **重點**：使用者不是填完一路送出，而是**每筆地各自走「產表1 → 編輯確認」**，累積 N+1 份表1 後，這一批**一起**送進表2、表3 做比較評分。

**先看這張總表**（一眼掌握有哪些 lambda、誰打它、進出什麼）；下面各小節再展開細節。

| lambda（程式名） | 白話用途 | 對外 API | 誰觸發 | 傳入（白話） | 傳回（白話） | 狀況 |

| `produce-survey` | 產**表1** 勘查表草稿 | `POST /api/produce/survey` | 畫面 1「開始查詢」 | 區段編號 + 比準地座標 | 表1（60 欄）+ 比準地條件 | ✅ 完整 |

| `regional-factor-grading` | 產**表2** 區域因素評分 | `POST /api/produce/regional-factors` | 畫面 2「確認」後 | 已確認的表1 + 比準地條件 | 各項優/普通/劣等級（⚠️ 格式對不上畫面） | ⚠️ 斷點 1 |

### 3.1 產表1 — `produce-survey`（勘查表產製 / 官方表3）

- **它是誰**：畫面 1 按「開始查詢」後呼叫的主程式。負責產出**表1（勘查表）的草稿**。
- **傳入什麼**：這塊地的區段編號 + 使用者在地圖標的比準地座標。
  - 技術對照：`{ sectionId, benchmarkLocation:{lat,lng} }`
- **傳回什麼**：一份表1 草稿，包含 60 個欄位（周邊有哪些學校/公園/公車站等，查得到的已填好、查不到的留空給人工），外加一份「比準地基本條件」資料（供後面表2/表3 用）。
  - 技術對照：`{ meta, survey（60 欄）, benchmark（比準地條件） }`
- **它自己還會做什麼**：內部去呼叫「查周邊設施」程式（§3.2）＋「AI 產草稿」程式，把結果組成表1。
- **目前狀況**：✅ 已完整實作，形狀符合契約。**這支是整條流程裡最完整的一段。**

### 3.2 查周邊設施 — `ntpc-facilities`（周邊設施查詢）

- **它是誰**：查「某個座標半徑內有哪些設施」的工具程式。不是使用者直接點的，是「產表1」和「產表3」在背後呼叫它。
- **傳入什麼**：一個座標 + 半徑（公尺）。
  - 技術對照：`GET ...?lon=&lat=&radius=`
- **傳回什麼**：範圍內的設施清單（每筆有類別、名稱、距中心幾公尺），加上分好六大類的彙總，加上附近門牌數量。
  - 技術對照：`{ area, facilities[], byCategory, doorplate }`
- **目前狀況**：✅ 已實作，形狀符合契約。

### 3.3 產表2 — `regional-factor-grading`（區域因素評分 / 官方表5）

- **它是誰**：畫面 3 進入時呼叫，產出**表2 草稿**——幫各項區域條件評「優／普通／劣」，並排出比準地 vs 比較標的。
- **傳入什麼（新契約）**：**N+1 份表1 定稿**——比準地 1 份 + 各比較標的各 1 份（每份都是使用者已編輯確認的表1）。
  - 技術對照：一個陣列，每筆 `{ meta, survey, benchmark }`（其中一筆標記為比準地，其餘為比較標的）。
- **傳回什麼（契約期待）**：一份 28 項的評分表，每項有「比準地的等級」和「各比較標的的等級 + 差值」。
  - 技術對照：`RegionalFactorRow[28]`（每列含 `subject` 比準地、`compare[]` 各比較標的）
- **關鍵事實**：`regional-factor-grading` 這支 lambda **一次只評「一筆地」**（cli README 明載「Base parcel only — no comparables」）。所以要有比較欄，必須**對 N+1 份表1 各跑一次這支**、再把結果合成——這正是斷點 1 的串接內容。
- **目前狀況**：⚠️ 單筆評分能跑，但「N+1 份 → 各評分 → 合成含比較欄 → 轉畫面格式 → 存檔」這條串接還沒接（斷點 1，見 §4.1）。

### 3.4 產表3 — `produce-comparison`（比較法估價表產製 / 官方表4）

- **它是誰**：畫面 4 進入時呼叫，產出**表3 草稿**——比準地 vs 比較標的逐項比較，算出試算價格。
- **傳入什麼**：使用者確認過的表2 + 同一批比較標的資料（含 N+1 份表1／比較標的宗地條件）。
  - 技術對照：`{ sectionId, regionalFactors, regionalTotal, benchmark, comparisonLocations[] }`（實作改合併鏈後輸入細節見 §4.2 / 表3合併-plan）
- **傳回什麼**：19 項個別因素的差異修正率、完整的表3 版式資料、試算價格。
  - 技術對照：`{ comparison（19項）, comparisonForm, computed }`
- **背後打的是哪個版本？**（常見疑問）**目前這支對外端點跑的是它「一開始的初始純規則版本」**——`lambda.ts` 只 import 自己目錄的 `rules.ts`（佔位係數）/ `compute.ts`（價格鏈）/ `mapToComparisonForm.ts`，**沒有呼叫 cli 的任何程式**（已用 grep 確認）。
- **正確方向：跟 cli 那條鏈「合併」，佔位版退役**。cli 的個別因素鏈**大部分做完了**：`individual-factor-grading`（判每項等級）+ `individualComparison`（比準地 vs 比較標的逐項排列、算 `delta`）+ `fillindividualAnlysis`（填表3 PDF）都已完成。**關鍵：cli 的 `delta` 就是修正率%（delta 15 = 15%）**，所以修正率並不缺。缺的只有兩塊、且都有現成來源：
  - **正常單價** → 呼叫 `land-transaction`（查該段實價登錄，先取最近一筆土地案例的 `unitPrice`）。
  - **試算價** → 用「正常單價 × (1 + 日期調整) × (1 + 區域修正) × (1 + Σ個別 delta)」算出（日期調整率**預設 0%**，前端當日填）。價格鏈公式可直接抄 `produce-comparison/compute.ts`。
- **目前狀況**：✅ `produce-comparison` 佔位版能跑但係數是暫時數字；**規劃改成「以 cli 鏈為主體 + land-transaction 正常單價 + compute 價格鏈」的合併版，端點 `POST /api/produce/comparison` 不變、佔位版退役**。這就是斷點 2 的接線內容，詳見 §4.2。接線 plan：[`infra/docs/表3合併-plan.md`](../infra/docs/表3合併-plan.md)。

### 3.5 存檔 — `case-store`（案件三表定稿儲存）

- **它是誰**：每張表使用者按「確認」時，把定稿存起來、之後可讀回的程式。契約文件（`API_INTEGRATION.md`）還沒正式定義它對外怎麼用，但程式已經寫好。
- **傳入什麼**：
  - 建一個案件：`{ sectionId, meta? }` → 拿到一個案件編號 `caseId`
  - 存表1：`?form=survey` + `{ caseId, survey, benchmark }`
  - 存表2：`?form=regional-factors` + `{ caseId, regionalFactors, regionalTotal }`
  - 存表3：`?form=comparison` + `{ caseId, comparison, comparisonForm, computed }`
- **傳回什麼**：存檔結果 / 讀回整個案件。
- **目前狀況**：✅ 已實作。它在流程裡的位置：**斷點 1 修好後，產出的表2 資料就是要存進這裡的 `?form=regional-factors`。**

### 3.6 上傳圖片 — `image-upload`（案件圖片上傳）

- **它是誰**：畫面 6 上傳照片時呼叫。契約文件還沒定義這步。
- **傳入什麼**：案件編號 + 檔名 + 圖片內容。
  - 技術對照：`POST { caseId, fileName, contentType, dataBase64 }`
- **傳回什麼**：存好的檔案位置；或列出某案已上傳的圖片。
- **目前狀況**：✅ 能存/列，**但「匯出時把這些圖併進報告 PDF」還沒接**（見 §4.3）。

### 3.7 匯出 PDF — `fill-district-survey` + `fill-report`（填表 + 合併）

## 4. 三個斷點（原始三個已全部接上；改記殘留缺陷）

> **狀態更新（2026-09-12）**：斷點 1／2／3 的**串接程式碼都已完成並部署**（🔵）——
> `produce-regional-factors`（表2 orchestrator）、`produce-comparison` v2 合併鏈（表3）、
> `export-report`（匯出 orchestrator）＋表2/表3 填表 lambda（`fill-regional-analysis` /
> `fill-individual-analysis`）都上雲了。`build:lambdas` + `cdk synth` 過、17 支 function。
>
> **但「結構通 ≠ 跑通且數字可信」。** 全線尚未端到端實測（🔵 非 🟢），且有四個殘留缺陷（見 §4.4）。
> 下面 §4.1–4.3 保留原斷點說明作為背景；當前該處理的是 §4.4。
>
> 每個斷點講四件事：**應該怎樣（契約期待）→ 實際怎樣 → 中間缺哪一段線 → 手邊已經有哪些現成零件**。

### 4.1 斷點 1（最關鍵）：表2 評分沒有「把 N+1 份表1 串成含比較欄的評分表」的串接者

- **缺 API 還是缺串接？** → **幾乎全是「既有 API/程式少了串接」，沒有缺任何新功能 API。** 要補的只有一支「串接者（orchestrator）」——它就是對外的 `POST /api/produce/regional-factors`，內部按順序打既有的東西，不做新運算。
- **應該怎樣**：收 **N+1 份表1 定稿**（比準地 + 各比較標的）→ 產出 28 項、含「比準地 + 各比較標的等級 + 差值」的評分表 → 存 `case-store`。
- **實際怎樣**：`regional-factor-grading` **一次只評一筆地**、回單筆巢狀原始評分（`graded.json`）；沒有東西把「N+1 份 → 各評分 → 合成 → 轉畫面格式 → 存檔」串起來。
- **要接的串接（照順序打既有東西）**：

  | 步驟 | 用什麼 | 現況 | 缺 API / 缺串接 |
  |---|---|---|---|
  | ① 對 N+1 份表1**各跑一次**評分 | `regional-factor-grading`（既有 lambda） | ✅ 已部署 | 缺串接（要迴圈呼叫 N+1 次） |
  | ② 合成「含比較欄」的中間格式 | `gradingComparison.buildFillReport`（既有純函式） | ✅ 已寫、測過 | 缺串接（沒 handler 呼叫） |
  | ③ 轉成畫面要的 28 項格式 | `mapRegionalComparisonToRows`（既有轉換） | ✅ 已寫、測過 | 缺串接（沒 handler 呼叫） |
  | ④ 存檔 | `case-store ?form=regional-factors`（既有 lambda） | ✅ 已部署 | 缺串接（沒人送 ③ 的結果進來） |

- **原本以為的「缺口 A」已被前端流程解掉**：先前擔心「比較標的沒有表1 可餵評分」。依定案，**比較標的也各走一次表1 產製 + 編輯確認**，所以進表2 時前端本來就會送 N+1 份表1 進來 —— ① 的輸入齊了，剩下純粹是後端把 ①②③④ 串起來。
- **契約改動（前端要配合）**：`POST /api/produce/regional-factors` 的 request 從「一份 `{survey,benchmark}`」改成「**N+1 份表1 定稿的陣列**」（比準地 + ≤3 比較標的，最多 4 份）；表3 同批沿用。
- **手邊現成零件**：評分 lambda、合成純函式、轉換函式、存檔 lambda **全部已有**。**只差一支 orchestrator 把它們串起來。**

### 4.2 斷點 2：表3 改用 cli 合併鏈（佔位版退役）

- **應該怎樣**：產表3 程式回 19 項修正率 + 完整表3 版式 + 試算價格。
- **實際怎樣**：對外端點目前跑的是 `produce-comparison` 的**初始純規則版**（形狀符合契約、能算出試算價，**但修正率係數是暫時填的佔位數字**）。cli 的個別因素鏈**並存、且大部分已完成**，但兩者**還沒整合**、還沒把對外端點切過去。
- **已定案的方向：合併**——以 cli 鏈為主體，補上「正常單價 + 試算價計算」，`produce-comparison` 佔位版退役、端點名不變。下表是合併後各塊由誰負責：

  | 表3 需要的東西 | 誰提供 | 狀態 |
  |---|---|---|
  | 每項個別因素**等級**（優/稍劣/劣） | cli `individual-factor-grading` | ✅ 已完成 |
  | 比準地 vs 比較標的逐項排列 + **`delta`（= 修正率%）** | cli `individualComparison`（`buildFillReport`，純 code） | ✅ 已完成（`delta` 直接就是修正率%） |
  | 各項**顯示值**（面積/道路…，表3 條件欄） | cli `comparison.json` | ✅ 已完成 |
  | **正常單價** | `land-transaction`（取最近一筆土地案例的 `unitPrice`） | 🔧 要接（v1 先取最近一筆土地） |
  | **日期調整率** | 預設 **0%**（前端當日填更準） | 🔧 直接給 0 |
  | **試算價 / `computed`** | 用「正常單價 ×(1+0%)×(1+區域修正)×(1+Σdelta)」算 | 🔧 抄 `produce-comparison/compute.ts` 公式 |
  | 表3 **PDF 版式** | cli `fillindividualAnlysis` | ✅ 已完成（未上雲，屬斷點 3） |

  > **修正正解**：cli 的 `delta` 就是修正率%，所以修正率**並不缺**（先前誤寫成「cli 缺修正率」，已更正）。真正要接的只有「查正常單價（land-transaction）」和「算試算價（抄 compute 公式、日期調整 0%）」兩塊。

- **`produce-comparison` 怎麼處理**：端點 `POST /api/produce/comparison` 沿用、**內部換成 cli 合併鏈**；佔位 `rules.ts` **丟掉**（delta 已是修正率），`compute.ts` 的價格鏈公式**搬過去保留**。佔位版退役。
- **待確認（v1）**：比較標的要跑評分需要它的宗地條件，但 request 只帶座標 → v1 先用「比較標的宗地條件 = 比準地」跑通（delta 多為 0、結構正確），真實比較標的條件後續再接。正常單價的多筆挑選 / 房地拆分也列後續。
- **接線 plan**：[`infra/docs/表3合併-plan.md`](../infra/docs/表3合併-plan.md)（含可派工 kickoff prompt）。

## 4.4 殘留缺陷（三斷點接上後，當前真正待補的）

三個斷點的「線」都接上了，但以下四項讓「經緯度 → PDF」**還不能算跑通且數字可信**。缺陷 1 是驗證、
2/3/4 有獨立 plan。

### 缺陷 1 — 尚未端到端實測（🔵 → 🟢 的最後一哩）
全 17 支已部署，但沒有人真的從「一個經緯度」一路打到「產出 PDF」驗證過。串通性目前是從 code 判讀，
非跑出來的。**下一步該做一次端到端實測**（見文末 checklist）。

### 缺陷 2 — 表3 數字是「結構正確、數值佔位」
`produce-comparison` v2 能出表3，但：
- **比較標的宗地條件**：request 的 `comparisonSurveys` 選填；沒帶時以「比較標的條件 = 比準地」跑，
  → 個別因素 `delta` 多為 0（結構對、數字不真）。
- **正常單價**：`land-transaction` 取「該段最近一筆土地案例」，查無回 0 → 試算價結構對、數值待調。
- 影響：表3 能產、能出 PDF，但**價格不能當真**。plan：[`infra/docs/缺陷2-表3數值-plan.md`](../infra/docs/缺陷2-表3數值-plan.md)。

### 缺陷 3 — 使用者上傳圖片實際併不進 PDF
`export-report` 只併「`image-upload` 回傳帶可抓 url 的圖」，但 `image-upload` 目前是 private bucket、
v1 只回 `s3Key`、不回可抓 url → 匯出時使用者上傳的圖**會被 skip**（export-report 自己註解寫明）。
影響：報告出得來，但**夾不進使用者上傳的照片**。plan：[`infra/docs/缺陷3-圖片匯出-plan.md`](../infra/docs/缺陷3-圖片匯出-plan.md)。

### 缺陷 4 — 前端契約已變更，需與前端對齊（⚠️ 未同步會直接串不起來）
斷點接線改了兩支對外 API 的 request 形狀，前端若不配合就打不通：
- **表2** `POST /api/produce/regional-factors`：request 從「單份 `{sectionId, survey, benchmark}`」
  → 改成「**比準地 1 份 + `comparables[]`（≤3 份表1 定稿）**」。
- **表3** `POST /api/produce/comparison`：request **新增 `comparisonSurveys[]`**（每個比較標的自己的
  表1 survey + benchmark），供各自評分；不帶則退化成「比較標的條件 = 比準地」。
- 這兩項已寫進 `API_INTEGRATION.md` 最下方「## 契約變更（2026-09，斷點接線後）」。**前端據該節調整**。

## 6. 端到端實測 checklist（缺陷 1）

一次從經緯度打到 PDF，逐棒確認回應。URL 取自各 stack 的 CfnOutput。

1. `POST <ProduceSurveyFunctionUrl>` `{ sectionId, benchmarkLocation:{lat,lng} }` → 回表1 草稿（survey + benchmark）。
2. （比準地 + 每個比較標的各重複 1）→ 收集 1+N 份表1。
3. `POST <CaseStoreFunctionUrl>` 建案 → `PUT ?form=survey` 存各份表1 定稿。
4. `POST <ProduceRegionalFactorsFunctionUrl>` `{ sectionId, benchmark:<表1>, comparables:[<表1>...] }` → 回 `RegionalFactorRow[28]`；確認 compare 筆數 = 比較標的數。
5. `POST <ProduceComparisonFunctionUrl>` `{ sectionId, regionalFactors, regionalTotal, benchmark, comparisonSurveys:[...] }` → 回 comparison + comparisonForm + computed；確認試算價有值（注意缺陷 2 數值佔位）。
6. `POST <ExportReportFunctionUrl>` `{ survey, regional:{purpose,content}, comparison, maps:[...], caseId }` → 回合併 PDF；確認頁數 = 表1+表2+表3+地圖(+圖片，注意缺陷 3)。

> 每一棒若非 200 就停下記錄狀態碼 + body，回報是哪支斷。
