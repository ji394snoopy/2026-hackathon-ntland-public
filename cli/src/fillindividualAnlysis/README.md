# fillindividualAnlysis

A standalone module that fills `input/individual-asnlysis.pdf` (表4 比較法調查估價表)
from `input/comparison.json` — `individualComparison`'s `FillReport` output — and writes
the result to `output/`. Not a Claude/Bedrock pipeline: no API calls, no AWS credentials,
nothing billed. Sibling to `src/fillRegionalAnlysis/` (same overall shape: extract
coordinates from the blank template's own text layer, fill from a comparison JSON), but a
single template rather than five, and matched by `categoryKey`/`itemKey` rather than raw
label text — see "Matching" below.

## Usage

```bash
npm run fill:individual

# only needed once, or after the template PDF changes:
npm run generate:individual-coords
```

`fill:individual` writes `output/individual-analysis-filled.pdf`.

## Inputs (all committed to git — nothing gitignored)

- `input/individual-asnlysis.pdf` — the blank 表4 template (A4 landscape,
  841.68×595.2pt).
- `input/comparison.json` — `individualComparison`'s `FillReport` output (see
  `src/individualComparison/README.md`): `categories[].items[].{base, comparables[]}`
  keyed by `categoryKey`/`itemKey`, `sectionIdBase`/`locationBase`/`comparableIdentities`,
  `totalScoreBase`/`comparableTotalScores`. Copied in from a real `individualComparison`
  run against `individualFactorGrading`'s checked-in sample case (新北市金山區金美段489
  地號 vs. 2 comparables).
- `input/coordinates.json` — generated by `generateCoordinates.ts` (see below) and
  committed for reuse, same treatment as `fillRegionalAnlysis/input/coordinates-*.json`.

## How coordinates are derived (no Bedrock call)

Like `fillRegionalAnlysis`, every position this module needs is real, positioned text on
`individual-asnlysis.pdf`'s own text layer — every item's row number (7-25), every
"條件"/"差異率" column header, and every static label ("地價區段"/"基本資料"/"其他"/
"合計") is printed, not blank. `extractCoordinates.ts` reads that text layer (via
`pdfjs-dist`'s `getTextContent()`) and computes coordinates deterministically:

- **Row y** comes from each item's own numbered-row text (`7`, `8`, ... `25`), matched at
  a fixed x anchor.
- **Column x** for the base/comparable 1/2/3 condition columns comes from the 4 real
  `"條件"` header occurrences (sorted by x) — filtered to `x ≥ 150`, since `"條件"` also
  appears as the 2nd line of the 2-line category labels (宗地/**條件**, 道路/**條件**,
  接近/**條件**, 行政/**條件**) at `x≈81-82`, far left of the real column headers
  (`x≈245+`). The 3 real `"差異率"` headers (comparable columns only) have no such
  collision.
- **A "simple" condition value** (a bare string like `"方形"`/`"70%"`/`"無"`) is drawn
  **centered** on that column's own `"條件"` header x, offset `+7.2` — calibrated by
  diffing this PDF's text layer against `references/example-page-3.pdf` (a real filled
  reference: same `CreationDate`/`ModDate` in `pdfinfo`, i.e. literally the same source
  file with values filled in, not a different rendering) and confirmed against 8
  independent samples (`方形`/`平坦`/`240%`/`70%`/`無`/`23`/`5`/`單面臨街`).
- **A `{name, distance, unit}` condition value** (e.g. `frontageRoadWidth`, the 5
  `proximityCondition` items, `presenceOfNoxiousFacility` — the same items
  `individualFactorGrading/benchmarkValue.ts` already treats as facility-type) gets
  **three separate calibrated anchors** in `coordinates.json`
  (`nameDistanceUnit.{name,distance,unit}`). `distance` is centered and `unit` is
  left-aligned on their own fixed per-column anchors, same as always. `name` is different:
  what looked like one wide `"條件"` column (name+distance+unit sharing one cell, per the
  PDF's own text layer, which has no headers narrower than `"條件"`) turned out, when the
  *blank* template was rendered to an image and scanned for real vector border pixels
  (`pdftoppm`/`pdfinfo`, not text — same technique the merged-region offsets below already
  used), to actually have **its own bordered sub-cell per field** — a real 71.4pt-wide
  name sub-cell, then a narrower distance sub-cell, then unit's. `distance`/`unit`'s
  stored anchors already fit safely inside their own sub-cells for every real value
  (short digits/units), so they're never at risk and are drawn at a fixed `FONT_SIZE`.
  `name` is the one variable-length field — `proximityToMarket`'s real facility name is 11
  characters (金山區第一零售傳統市場), 66pt wide at this module's font/size, close to that
  71.4pt sub-cell's full width. `name.x` is stored as that sub-cell's **right edge**
  (`nameDistanceUnit.name.leftBound` is its left edge) and drawn **right-aligned**
  (`pushRightAlignedFit` in `fillEngine.ts`), not centered: a short name like `中山路`
  sits flush against `distance` exactly as a human editor manually tuned it to (see next
  paragraph), and a long name grows leftward into its own sub-cell's room instead of
  rightward into `distance`'s. Only if a name would still cross `leftBound` does it shrink
  (down from `FONT_SIZE`, no floor) — `distance`/`unit` never shrink. In the checked-in
  `comparison.json`, only `proximityToMarket`'s comparable-2 cell shrinks, and barely
  (~4%, `maxWidth` 63.36pt vs. its 66pt name) — every other cell, including that same name
  in every other column, renders at the full `FONT_SIZE`.
  - **`coordinates.json` is now hand-maintained, not regenerated.** `frontageRoadWidth`'s
    base/comparable-1/comparable-2 `name.x` were manually edited (from
    `extractCoordinates.ts`'s uniform per-column formula, `headerX + 13.2` treated as a
    *center*) after visually confirming the formula's default centered position let 中山路
    overflow across the name/distance sub-cell border. That manual fix is the reference
    every other `nameDistanceUnit` row's `name.x`/`leftBound` was set from (right edge =
    old manually-tuned center + `measureText("中山路")/2` = +9pt, which reproduces 中山路's
    exact rendered pixels since right-aligning a value at its own center ± half-width is
    identical to centering it). Running `npm run generate:individual-coords` again would
    silently overwrite this calibration with the old uniform-center formula and reintroduce
    the overflow — don't run it against this file anymore.
  - **Comparable 3's `name.x` had never been visually exercised** (the checked-in
    `comparison.json` used to only populate comparables 1-2) and, unlike base/1/2, was
    still the raw `extractCoordinates.ts` formula value carried forward, never corrected
    against 中山路 — it turned out to overshoot the real name/distance sub-cell border by
    ~7pt (703.2 vs. the border's actual 696.24pt, confirmed the same border-pixel-scan
    way as everywhere else in this section), so every comparable-3 `nameDistanceUnit`
    name rendered crossing the border, 中山路 included. Fixed by setting comparable 3's
    `name.x` to 691 (a ~5pt margin, in line with base/1/2's 3.8-7.9pt margins) once
    `comparison.json` was extended with real comparable-3 values — confirmed by
    re-rendering every comparable-3 `nameDistanceUnit` row.
  - `roadType`'s value is a plain string (not `{name,distance,unit}`), so its own
    `condition.x`/`.../3` (not `nameDistanceUnit`) control its rendered position; these
    were nudged 8pt left of every other simple-condition row's shared anchor, by request,
    scoped to just this one item (other rows sharing that same default anchor are
    untouched).
- **Each item row's `percent` cell (差異率 sub-column, the signed percentage like
  `+104.75％`)** was originally left-aligned starting right after the `"差異率"` header —
  fine for short values but a longer signed percentage (e.g. `+104.75％`, `+40.00％`) ran
  rightward across the column's real right border into the next comparable's own
  `實例編號` column. Fixed the same way as `nameDistanceUnit.name`: `percent` is now
  drawn **right-aligned** and shrinks (down from `FONT_SIZE`, no floor) only if it would
  still cross its own sub-cell's left border, via the same `pushRightAlignedFit` helper.
  `coordinates.json`'s `percent.rightX`/`percent.leftBound` (added alongside the
  pre-existing `percent.x`/`.y`, which `otherFactors`'s `"-"` placeholders still use via
  `pushCentered`) were **not** derived from the text layer — this template's 差異率
  sub-column has no header text narrower than the merged `"條件"`+`"差異率"` region to
  anchor off of the way `nameDistanceUnit.name.leftBound` could. They come from a direct
  border-pixel scan of the blank template (`pdftoppm -r 300`, scanning for pixel columns
  dark across the full item-table height, same technique as the merged-region offsets
  above): each comparable's 差異率 sub-column is a uniform ~27.9pt-wide block (divider
  at `headerX+70.1`ish, right border ~27.9pt further right — comparable 1
  `[444.17,469.0]` with 1.5pt margins already applied, comparable 2 `[598.21,623.15]`,
  comparable 3 `[752.49,777.44]`), consistent across all 3 comparables and confirmed
  against the merged-region math (`MERGED_REGION_COMPARABLE_CENTER_OFFSET`) independently
  landing on the same right-border x.
- **`sectionIdBase`/`comparableIdentities[].sectionId`** (地價區段 row) is left-aligned at
  `headerX − 4.92`, `y = labelY + 0.6` — confirmed identical offset on both base and
  comparable 1 columns in the reference (240.41 vs 245.33, 367.63 vs 372.55).
- **`locationBase`/`comparableIdentities[].location`** (0基本資料 row) and the **合計**
  (grand-total) row's `comparableTotalScores[].delta` are centered in a **merged**
  per-comparable cell, physically different from the item rows' 條件-only column — a real
  bug in the first calibration pass, found by comparing the rendered output PDF against
  `references/example-page-3.pdf` directly (not just text-layer diffing): the original
  approximation reused the item-row simple-condition offset (`headerX + 7.2`) for every
  column, which rendered correctly for the base column but visibly sat too far left for
  every comparable column. Fixed by measuring the reference PDF's actual rendered border
  *pixels* (`pdftoppm` output, scanning for columns dark across a full row's height — the
  text layer alone has no vector/line info) rather than just its text: base's merged cell
  is `[188.28, 316.26]pt` (center `headerX + 6.94`, ≈ the item-row offset by
  near-coincidence — it's the same physical column, since base never has a 差異率
  sub-column to merge away), while every comparable's merged cell is a uniform
  `~154.4pt`-wide block whose center is `headerX + 20.93` — confirmed via 3 independent
  border measurements (comparable 1/2/3 all measured `20.91`-`20.96`) and, separately, by
  re-measuring the item rows' own (narrower) condition-column borders and finding their
  comparable-column center lands at `headerX + 7.2` almost exactly (`379.53` measured vs.
  `379.75` computed) — two independent measurement methods (text-anchor diffing and
  border-pixel scanning) agreeing confirms neither offset is overfit noise.
  `MERGED_REGION_BASE_CENTER_OFFSET`/`MERGED_REGION_COMPARABLE_CENTER_OFFSET` in
  `extractCoordinates.ts` are these two offsets. **A second, separate bug on top of the
  offset itself:** `fillEngine.ts` was drawing these three fields (`locationBase`,
  `comparableIdentities[].location`, `comparableTotalScores[].delta`) with
  `pushLeftAligned` even though `extractCoordinates.ts` computed them as **center**
  points — so the text was drawn starting *at* the center and running rightward, instead
  of straddling it. This is what actually produced the "text needs to move left" symptom
  (confirmed by reading the real output PDF's own drawn coordinates: the text's left edge
  was literally the calibrated center value). Fixed by switching those three draw calls
  to `pushCentered`; `sectionIdBase`/`comparableIdentities[].sectionId` correctly stayed
  `pushLeftAligned` (those two really are left-aligned anchors).
- **Category-level subtotals (`category.totalBase`/`category.comparableTotals`) are never
  drawn — this PDF template has no per-category subtotal row at all.** Unlike
  `fillRegionalAnlysis`'s 表5-2 (one `百分比小計` row per category), 表4 has only 25 item
  rows, one always-empty "6其他" row, and a single case-level "合計" row. This is a known,
  intentional gap: the data exists in `comparison.json`, `coordinates.json` simply has no
  slot for it.
- **The case-level base total (`totalScoreBase`) is never drawn**, matching
  `fillRegionalAnlysis`'s convention — independently confirmed here too: the reference's
  "合計" row only has a value under 比較標的1's merged column, nothing under 比準地.
  `comparableTotalScores[].delta` is still drawn per comparable.
- **The always-empty "6其他" category** (`items: []`) draws a literal `"-"` in the base
  condition cell and every comparable's condition + 差異率 cells, matching exactly what
  `references/example-page-3.pdf` draws there (`"-"` at the same column-center offset as
  every other simple condition value — no special-casing needed).

## Matching: categoryKey/itemKey, not raw label text

Unlike `fillRegionalAnlysis` (which matches on normalized raw Chinese labels, since
`regionalAnalysis`'s other 4 purposes have no matching vocabulary), this template's 19
items line up 1:1 with `references/factor-standard.json`'s `individualFactors` tree
(`lotCondition`:6, `roadCondition`:2, `proximityCondition`:5, `surroundingEnvironment`:2,
`administrativeCondition`:4 — confirmed via direct inspection this session), in the same
order as the PDF's own numbered rows 7-25. `extractCoordinates.ts` hardcodes this
19-entry `{categoryKey, itemKey}` order (`ITEM_KEY_ORDER`) and zips it positionally
against the 19 row y's it extracts; `fillEngine.ts` then matches
`comparison.json`'s items by `categoryKey::itemKey` directly. This sidesteps a real
wording mismatch found during investigation: the PDF prints row 11 as `"臨街情形"`, but
`factor-standard.json`/`comparison.json` both say `"臨路情形"` — label-matching would need
a hand-added alias (as `fillRegionalAnlysis`'s README documents for its own
環境污染/環境汙染 typo); key-matching doesn't care.

## Known gaps

- **Category-level subtotals have nowhere to go on this template** (see above) — not a
  bug, just a PDF structure difference from `fillRegionalAnlysis`'s 表5-2.
- **`locationBase`/`comparableIdentities[].location` and the 合計 row's offsets are now
  independently confirmed** (border-pixel measurement, see "How coordinates are derived"
  above) rather than approximated, but only against this module's own font/size
  (`ARPLUKaiTW-Book.ttf` @ 6pt) — a much longer location string than the checked-in
  case's (14 chars) hasn't been stress-tested for overflow past the merged cell's own
  border.
- **`proximityToMarket`'s real facility name (11 chars) is the only row that currently
  triggers the shrink-to-fit path** — every other item in the checked-in
  `input/comparison.json` renders at full `FONT_SIZE`. A future case with several very
  long facility names, or `comparable 2`/`comparable 3` both populated with long names,
  hasn't been visually exercised.
- **Only comparable 1 and comparable 2 are populated** in the checked-in
  `input/comparison.json` (the underlying case only has 2 comparables); comparable 3's
  columns render correctly empty (confirmed in the rendered PNG) but the template's own
  comparable 3 column has never been exercised with real content.
- **案號/估價基準日/土地正常單價/交易日期/調整百分率/調整至估價基準日單價/
  區域因素調整百分率/比較價格 block (調整百分率絕對值加總/試算價格/比準地比較價格)/
  備註欄 have no corresponding field in `comparison.json`** and are left blank — no
  fabricated placeholder, per explicit instruction (`references/example-page-3.pdf`
  happens to show real values there, but they come from a different, unrelated part of
  the appraisal pipeline that doesn't exist yet).
