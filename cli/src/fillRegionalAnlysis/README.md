# fillRegionalAnlysis

A standalone module that fills the correct 表5-1~5-5 影響地價區域因素分析明細表 PDF
template — chosen by land-use purpose (agricultural/commercial/industrial/other/
residential) — from `input/comparison-<purpose>.json`'s per-item grade+percentage
data, and writes the result to `output/`. Not a Claude/Bedrock pipeline: no API calls,
no AWS credentials, nothing billed. This is the "future PDF-fill step"
`src/gradingComparison/README.md` describes `comparison.json`'s (the shape's own
name there) shape as existing for.

## Usage

```bash
npm run fill:regional -- commercial     # or agricultural/industrial/other/residential

# only needed once, or after a template PDF changes:
npm run generate:regional-coords                 # regenerates all 5 coordinates-<purpose>.json
npm run generate:regional-coords -- commercial    # regenerates just one
```

`fill:regional` writes `output/regional-analysis-<purpose>-filled.pdf`.

## Inputs (all committed to git — nothing gitignored)

- `input/regional-anlysis-{agricultural,commercial,industrial,other,residential}.pdf`
  — the 5 blank form templates (表5-1/5-2/5-3/5-4/5-5). `commercial`'s file was
  renamed this session from `regional-anlysis-commerical.pdf` to fix a typo.
- `input/comparison-<purpose>.json` — content data in `gradingComparison`'s
  `FillReport` shape (`categories[].items[].{base,comparables[]}`,
  `totalBase`/`comparableTotals`, `totalScoreBase`/`comparableTotalScores`,
  `sectionIdBase`/`comparableSectionIds`), one per purpose. `main.ts` reads
  `comparison-${purpose}.json` for whichever purpose it's run with — there's no
  single default anymore. `comparison-commercial.json` (renamed from
  `comparison.json` this session, matching this same-per-purpose naming) is the only
  one with real appraisal content; the other 4 (`comparison-{agricultural,
  industrial,other,residential}.json`) are synthetic smoke-test fixtures — every
  item set to 優/rate 1/delta 0 with `categoryRaw`/`itemRaw` copied verbatim from
  that purpose's own `coordinates-<purpose>.json` — that exist only to exercise
  those 4 purposes' coordinate files end-to-end (see "Known gaps" below), not to
  represent a real appraisal.
- `input/coordinates-<purpose>.json` — one per purpose, generated by
  `generateCoordinates.ts` (see below) and committed for reuse, same treatment as
  `fillDistrictSurvey/input/coordinates.json`.

## How coordinates are derived (no Bedrock call)

Unlike `districtSurvey`'s calibration step (which sends the PDF to Claude and asks it
to report pixel positions), every position this module needs is already real,
positioned text in these PDFs' own text layer — every category/item label and every
column header (優劣等級 ×4, 修正百分比 ×3) is printed, not blank. So
`extractCoordinates.ts` reads that text layer (via `pdfjs-dist`'s `getTextContent()`)
and computes coordinates deterministically:

- **Row y** comes from each category/item label's own baseline.
- **Each grade cell has two sub-values**, not one: a numeric "rate" (1-5, left-aligned)
  and the grade text itself (優/稍優/普通/稍劣/劣, drawn *centered*, not left-aligned —
  confirmed against `references/example-page-2.pdf`, a real filled reference example,
  by comparing a 1-char grade like 優 against a 2-char grade like 普通 in the same
  column: both runs' left edges differ by exactly half a character width, the
  signature of centering). The `優劣等級` header only marks the column's rough left
  edge; it doesn't tell you where these two sub-values actually sit, or that there even
  are two. Same for `修正百分比`: it's left-aligned at a specific offset from the
  header, not right-aligned to a shared column edge, and item-row values are *bare
  numbers* (no `％`) — only subtotal/grand-total rows get a `％` suffix, drawn by
  whoever filled the reference, not pre-printed on the blank template. None of this is
  derivable from the blank template's headers alone (a blank template has no printed
  修正百分比 value at all to calibrate against), so these offsets are calibrated once
  against the reference and reused as fixed relative offsets from each PDF's own
  (correctly, deterministically extracted) header positions — see
  `extractCoordinates.ts`'s own header comment for the exact numbers and how each was
  derived. The reference is a *different rendering* of the form (different absolute
  margins/row-spacing than the blank template this module actually fills), so its
  absolute x/y aren't reusable directly — only the *offset* of each value from that
  column's own header, measured within the reference itself, transfers.
- **Column x** for rate/grade-center/percent all key off the 4 `優劣等級` header
  positions (base + 3 comparables) and the 3 `修正百分比` header positions — all 7 are
  real, individually measured text on every PDF, so none of the 4 columns need pitch
  extrapolation from another one.
- **Wrapped labels** (a long item name printed on two lines) are merged back into one
  string via a y-gap threshold — continuation lines sit much closer together than
  genuinely new rows. This gap is **derived per PDF**, not a fixed constant: measured
  values were 10.56pt (commercial), 10.68pt (residential), and 11.64pt (agricultural/
  industrial/other) — different templates, different line-height. The threshold is
  found by sorting a column's gaps ascending and taking the midpoint of the first jump
  bigger than 0.5pt from the bottom (the point where the "wrapped line" cluster ends
  and the "new row" cluster begins). This needs a reasonably large, representative
  sample to work — every one of the 5 real PDFs has one (19-29 items), so this isn't a
  practical risk, but a hypothetical document with zero wrapped labels anywhere would
  have nothing for it to anchor on.
- **Category boundaries** come from the `百分比小計` (subtotal) marker rows, one per
  category, in printed order. `extractCoordinates.ts` still derives a `totalBase`
  position for each category (base's own subtotal cell, in the merged region near
  comparable 1's grade column, not under base's own header), but `fillEngine.ts`
  **never draws it** — per explicit user instruction, `category.totalBase` from
  `comparison-<purpose>.json` is intentionally skipped for every category, base-column
  subtotal cells are always left blank. `comparableTotals[].delta` (each comparable's
  own subtotal) is unaffected and still draws normally.
- **Grand-total row** is located via the `=(1)+(2)+...` formula string (works
  regardless of how many categories that purpose has, 6-8 across the 5 templates).
  Same treatment as category subtotals: `content.totalScoreBase` (the 比準地 column's
  own grand-total) is **never drawn** — per explicit user instruction —
  while `comparableTotalScores[].delta` (each comparable's own grand-total) still is.
- **`sectionIdBase`/`comparableInstanceIds`/`comparableSequenceNumbers`** all come from
  the `地價區段號`/`比準地`/`實例編號` label positions, but map to two *different*
  pieces of content at two *different* rows, not one:
  - `sectionIdBase` (base's own 地價區段號) and `comparableInstanceIds` (each
    comparable's own 地價區段號) draw `comparison-<purpose>.json`'s `sectionIdBase`/
    `comparableSectionIds[].sectionId` — confirmed from the reference: the
    `地價區段號` row prints one section-id value per column (比準地 *and* each
    比較標的), not just base's. `comparableInstanceIds.y` is set to `sectionIdBase.y`
    (each comparable's own real `實例編號`-label x, but base's `地價區段號` row's y) —
    it's a real merged cell spanning that comparable's whole column, so it sits on
    that same row, not "below the 實例編號 label" as a raw measurement from that label
    alone would suggest (confirmed against `input/coordinates-commercial.json`, hand-
    tuned against a real filled PDF, where the two y's are exactly equal).
  - `comparableSequenceNumbers` is a separate position — drawn on the `實例編號`
    label's own row, offset right into the blank space *after* that label's text (the
    same x every comparable's item-row `修正百分比` value uses) — for 實例編號's own
    value, which has **no corresponding field in `comparison-<purpose>.json` at all**.
    It isn't looked up from content; `fillEngine.ts` just counts how many entries
    `content.comparableSectionIds` has and draws `1`..`n` in that order, positionally —
    so it reflects how many comparables are actually present, not whatever string
    their own `label` field happens to carry. Kept deliberately distinct from
    `comparableInstanceIds` (different row *and* different x) so the two values can
    never collide — confirmed against `input/coordinates-commercial.json`'s own
    hand-tuned values (`x` matches item-row `修正百分比` x almost exactly; `y` sits on
    the label's own row, ~1.7pt above it).
  - `comparableTotals[].percentX`/`comparableTotalScores[].percentX` (the `百分比小計`
    subtotal and grand-total cells) draw in that same merged-cell region as
    `comparableInstanceIds`, reusing its x — not the narrow `修正百分比` item-column x
    `comparablePercentXFor` gives item rows. Confirmed against
    `input/coordinates-commercial.json`: its `comparableTotals`/`comparableTotalScores`
    `percentX` values (282/385/485) match `comparableInstanceIds`' x exactly, not the
    item rows' `percentX` (324.91/423.67/522.46).

Validated against real position dumps of all 5 PDFs before implementing, against
`comparison-commercial.json` after (27 of its 28 commercial items match by label — see
"Known gaps"), and against `references/example-page-2.pdf` (a real filled reference
example) for the rate/grade-center/percent offsets — rendered to PNG via `pdftoppm` and
visually compared both before and after that calibration. The `comparableInstanceIds`/
`comparableSequenceNumbers`/`comparableTotals`/`comparableTotalScores` merged-region
fix (see above) was validated the same way: regenerated for the 4 non-commercial
purposes via `npm run generate:regional-coords -- <purpose>`, then rendered to PNG and
compared against `comparison-commercial.json`'s already-correct layout — in each of the
4, the `1`/`2`/`3` sequence numbers are now visible next to their `實例編號` labels
(no longer hidden under the `地價區段號` value), and every `百分比小計`/grand-total
percentage now lands in the same merged-cell position commercial's does.

## Matching: raw label, not itemKey/categoryKey

`comparison-<purpose>.json`'s `categoryRaw`/`itemRaw` are **abbreviated summaries of
the PDF's fuller printed text**, not verbatim substrings, and not applied one
consistent way:

- Some items drop the whole bracketed clause: PDF `有無限制建築（整體開發、面積限制、
  高度限制……等）` → content `有無限制建築`.
- Others unwrap the bracket into plain text: PDF `都市計畫（內、外）` → content
  `都市計畫內外`.

`fillEngine.ts` handles both by computing two normalized variants per label (the whole
bracketed span removed, and just the bracket/comma punctuation removed with content
kept) and matching if any variant agrees on either side. This is also why matching
uses the raw Chinese label at all, instead of `itemKey`/`categoryKey` the way every
other pipeline in this repo does — `factor-standard.json`'s `regionalFactors`
vocabulary only covers the commercial (表5-2) item set, so the other 4 purposes'
items (日照, 景觀, 接近學校, 農地改良, 傾斜度, ...) have no key at all to match on.

Any category/item present on one side but not the other (by either side's own
matching, after normalization) is skipped with a `console.warn`, never thrown — this
was the common case before every purpose had its own `comparison-<purpose>.json`
(see below); it now only fires for a genuine label mismatch.

## Known gaps

- **All 5 `coordinates-<purpose>.json` files are now on the current schema.** The
  rate/gradeCenter/percent calibration against `references/example-page-2.pdf`
  (described above) only has direct reference confirmation for `commercial` — the
  other 4 purposes' offsets are shared/extrapolated from that same calibration, not
  independently confirmed against a filled example of their own. Regenerated via
  `npm run generate:regional-coords -- <purpose>` and spot-checked: numerically (each
  computed `rateX`/`gradeCenterX`/`percentX` matches its documented fixed offset from
  that PDF's own `優劣等級`/`修正百分` header positions, independently recomputed from
  the raw text layer) and visually (agricultural and residential rendered to PNG with
  markers at every computed coordinate — every cell, including multi-line wrapped
  labels, lands correctly; industrial/other were only schema- and numerically-checked,
  not rendered).
- **Only `commercial` has real appraisal content; the other 4 have synthetic
  smoke-test content.** `comparison-commercial.json` (renamed from `comparison.json`
  this session) is real appraisal data. `comparison-{agricultural,industrial,other,
  residential}.json` exist so each purpose's `coordinates-<purpose>.json` could
  actually be exercised end-to-end (confirmed: `npm run fill:regional -- <purpose>`
  for all 4 prints no `console.warn` label-mismatch lines, and every category/item
  fills), but every value in them is a placeholder (優/rate 1/delta 0, `sectionIdBase`
  `"TEST-<PURPOSE>"`) generated directly from each coordinates file's own
  `categoryRaw`/`itemRaw` labels — not a real appraisal case. The other 4 purposes'
  PDFs have structurally different category/item sets from commercial's (confirmed
  via each PDF's own text layer — not just a subset, genuinely different items), so
  filling any of them with real appraisal data still requires land-use-specific
  content sourced from an actual case, which doesn't exist yet.
- **`環境污染`/`環境汙染` — a real one-character typo, resolved with hand-added
  aliases, not a code fix.** The commercial PDF prints `環境污染` (污, U+6C61);
  `comparison-commercial.json` has `環境汙染` (汙, U+6C5A) — a different character,
  not a bracket/punctuation difference normalization can bridge.
  `comparison-commercial.json`'s item under that category also uses a short summary
  phrasing (`環境污染之有無及接近程度`) that isn't a bracket-stripped variant of the
  PDF's itemized `水污染、噪音污染、廢氣污染、廢棄物污染等之有無及接近程度` either.
  `input/coordinates-commercial.json` now carries **both** the category and the item
  twice — the real strings from `extractCoordinates.ts` (`環境污染` /
  `水污染、噪音污染...`) plus hand-added aliases matching `comparison-commercial.json`'s
  exact wording (`環境汙染` / `環境污染之有無及接近程度`), all four pointing at the
  same physical row's coordinates — so this category now fills in completely, matching
  every other category. **These hand-added aliases are not regeneration-safe**:
  running `npm run generate:regional-coords -- commercial` overwrites the whole file
  from the PDF's own text layer again, which never produces the alias strings — they'd
  need to be re-added by hand afterward, or the upstream typo/phrasing mismatch fixed
  in `comparison-commercial.json` instead.
- **A pre-existing stray `"0.00"`** already sits in the commercial PDF template itself
  near 停車場地之便利程度's 3rd-comparable percent cell (confirmed in the template's
  own text layer before this module draws anything) — cosmetically overlaps this
  module's own `0.00%` draw there when that cell's value is genuinely zero. A template
  quirk, not something this module can or should suppress.
- **案號 (case number)** has no field anywhere in `comparison-<purpose>.json`, so it's
  never requested or drawn — left blank on the output PDF.
